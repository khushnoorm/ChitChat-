Honest, Transparent Security Architecture

We distinguish clearly between transport/database rule protection and client-side end-to-end encryption.

🔒 Standard Mode: TLS + Firestore Security Rules

  • • Participant Isolation: Every conversation document stores a locked 2-user participants array verified on every read and write.
  • • Anti-Impersonation: Firestore rules verify request.resource.data.senderId == request.auth.uid and enforce server timestamps (request.time).
  • • Abuse & Block Controls: Blocking a user immediately halts message creation in Firestore rules as well as the interface.

🗝️ E2EE Mode: WebCrypto ECDH P-256 + AES-256-GCM

  • • Device Key Generation: Your browser generates an ECDH P-256 keypair. The private key stays in local device storage; only the public JWK is shared.
  • • Per-Message Encryption: When E2EE is toggled on in a chat, messages are encrypted client-side with a derived 256-bit AES-GCM key and unique 96-bit IV before reaching Firestore.
  • • Key Verification: Compare SHA-256 public key fingerprints with your contact to verify identity.
